# File & Folder Architecture

Applies to all new code and refactors. This file governs the **shape** of code. Only create folders marked *(planned)* when a real need appears.

## 1. Size limits

| Kind | Target | Hard limit |
|---|---|---|
| Component `.tsx`, module `.ts` | ≤ 200 lines | 300 lines |
| Function | ≤ 40 lines | 60 lines |
| Longest line | ≤ 120 cols | 160 cols |
| Barrel / `index.ts` files | not used | n/a |

- Over target: split **before** adding the feature. Do not split unrelated files just to hit a number.
- Exempt: `src/components/ui/` (shadcn), `src/app/globals.css`, static data.
- One file = one responsibility. Signs it must split: section-divider comments, many unrelated `useState`, a name containing "and" or "utils".
- Do not create `utils.ts`, `helpers.ts`, `common.ts`, `misc.ts`. Exception: `src/lib/utils.ts` (shadcn `cn`), nothing else goes in it. Name files by content (`price-format.ts`).

## 2. Folder map

This is the intended layout (what each folder is for), not an inventory. The actual files and routes are in `PROJECT_MAP.md`, generated by `npm run map`: search it with grep, never read it whole. Run `npm run map` after any structure change.

```
src/
  app/                 Routing only: page, layout, route handlers. Thin, no business logic.
    api/<domain>/      Route handlers: parse request -> call lib/server -> respond.
  components/
    ui/                shadcn primitives. Domain-free. Add via CLI only.
    <feature>/         Components of one feature (create when >= 3 related files).
    <area>/            A feature area with several pages (e.g. dashboard). Holds folders only, see "Feature areas".
      shell/           The area's frame: layout parts, navigation, header, footer.
      shared/          Pieces used by >= 2 pages of the area (mock data, common copy, cards).
      <page>/          One folder per route of the area, even with a single file.
  lib/                 Client-safe code: contracts/validation, API clients, formatting.
    server/<domain>/   Server-only (DB, auth, payments, external providers). `import "server-only"`.
      db/              Drizzle client (`client.ts`) and `schema/` (one file per domain).
  hooks/               (planned) Cross-feature hooks only. Feature hooks live in the feature folder.
drizzle/               SQL migrations generated by drizzle-kit. Never hand-edit.
docker-compose.yml     Local PostgreSQL. Config in `.env.local` (from `.env.example`), passed with `--env-file`.
public/                Static assets.
tasks/                 Audits, designs, reports. Not a contract.
```

### Where does new code go?

| Creating | Location |
|---|---|
| Page / route | `src/app/` (thin; logic in components or `lib/server`) |
| HTTP endpoint | `src/app/api/<domain>/.../route.ts` calling `src/lib/server/<domain>/` |
| Validation / types shared by client and server | `src/lib/<name>-contract.ts` |
| DB access, auth, payments, external providers | `src/lib/server/<domain>/` + `import "server-only"` |
| Component of one feature | `src/components/<feature>/` |
| Component of one page in an area | `src/components/<area>/<page>/` |
| Pages that share a layout but no URL segment | route group `src/app/(<area>)/` |
| Component used by several features | `src/components/<name>.tsx` (no cross-feature imports) |
| UI kit shared by dashboard and admin | `src/components/app-kit/` |
| Owner's two-tone icons used by more than one area | `src/components/icons/{ui,content}/` (one file per icon); area-only icons in `<area>/shared/icons/` |
| Area with its own URL segment (admin) | `src/app/<area>/`, its framed pages in a route group `src/app/<area>/(<group>)/` |
| Client HTTP calls | `src/lib/<name>-client.ts` (components never call raw `fetch`) |
| Large static data | its own data file |
| Tests | `*.test.ts` beside the pure module |

## 3. Dependency direction (one way, no cycles)

```
app  ->  components  ->  lib (client-safe)
app/api  ->  lib/server  ->  lib (contract)
```

- `components/*` and `lib/*.ts` never import `lib/server/*`.
- `lib/server/*` never imports `components/*` or `app/*`.
- Feature folders do not reach into each other. Shared needs move up to `components/<name>.tsx` or `lib/`.
- Inside an area: `<page>/` -> `shared/`, `shell/` -> `shared/`; never `<page>/` -> another `<page>/`.
- Validate input once in a `*-contract.ts`, used by both client and server. Never duplicate schemas.

## 4. Naming and structure

- Files/folders `kebab-case`; components `PascalCase` inside the file; one main component per file.
- Suffix vocabulary: `*-contract.ts`, `*-client.ts`, `use-*.ts`, `*-form.tsx`, `*-view.tsx` (pure display), `*-page.tsx` (loads data, renders view).
- Colocate: a feature's components, types and data live in one folder.
- New folder only for >= 3 related files. If >= 3 files in `lib/` share a prefix, move them into a folder.
  Exception: page folders inside a feature area (below) exist from the first file.
- A folder holds at most ~10 files, tests included. Past that, group them by what they belong to before adding more.

### Feature areas

A feature with several pages (one route each), such as the dashboard, is an area, not one flat folder.

- The area root holds folders only: `shell/`, `shared/` and one `<page>/` per route. No loose files at the root.
- `<page>/` holds that page's view, its parts, its copy (`<page>-copy.ts`), its page-only data and its tests.
- A piece moves to `shared/` only when a second page imports it; until then it stays in its page folder.
- Pages import from `shared/` and `shell/` of their own area, never from another page folder.
- Routes mirror the area: `src/app/(<area>)/<page>/page.tsx` renders `components/<area>/<page>/<page>-view.tsx`.
- Route handlers export only HTTP methods + `runtime`/`dynamic`; logic goes in `lib/server`.
- CSS: Tailwind v4 CSS-first. One global entry `src/app/globals.css` (tokens, `@theme inline`, base). Style with utilities in TSX. No new per-feature `.css` files.

## 5. Reliability

1. Keep side effects apart from pure logic (format, validate, compute) so it is testable.
2. Explicit errors: never swallow. Use typed error classes; server uses one central `AppError` in `lib/server/errors.ts`.
3. No third copy: copying twice is fine, the third time extract a clearly named module.
4. No dead code: delete retired features with their data and routes.
5. Keep docs true: paths mentioned in `AGENTS.md` and `.claude/rules/` must exist (or be marked *(planned)*). Check against `PROJECT_MAP.md` when editing them.

## 6. Enforcement

Automatic: `npm run lint`, `npx tsc --noEmit`. Size limits, dependency direction and naming are reviewed manually. Add ESLint import rules or a size checker only on explicit request.
